# 量化表述词库：模糊 → 量化改写对照

## 一、改写原则

量化的目的不是堆砌数字，而是让事实**可验证**。优先级：

1. **精确数字**：完成 3 个需求、修复 7 个缺陷、响应时间从 800ms 降到 210ms
2. **规模/范围**：覆盖 5 个模块、涉及 2 个团队、整理 40 页文档
3. **对比/变化**：较上周减少 60%、从每天 3 次降到每周 1 次
4. **状态锚点**：已上线 / 已评审通过 / 已合并主干 / 已交付客户验收

没有数字时，用第 2–4 级替代，**不允许**退回模糊表述。

## 二、高频模糊表述对照表

| 模糊表述（禁止直接出现） | 改写方向 | 示例 |
| --- | --- | --- |
| 积极推进 / 推动了 | 写出具体动作 + 当前状态 | 完成方案评审，进入开发阶段 |
| 持续优化 | 优化了什么 + 效果如何度量 | 接口平均耗时从 800ms 降至 210ms |
| 大量工作 / 很多 | 数量或范围 | 梳理 6 个历史遗留问题，关闭其中 4 个 |
| 深入调研 / 研究 | 产出物是什么 | 输出对比报告 1 份，覆盖 3 个候选方案 |
| 配合 / 协助 | 自己的具体贡献 | 负责接口联调部分，完成 12 个用例 |
| 基本完成了 | 剩余部分是什么 | 主体功能完成，剩余异常处理（预计 1 天） |
| 取得不错效果 | 谁观察到的什么变化 | 客户验收一次性通过，无返工项 |
| 加强了沟通 | 沟通产生了什么决定 | 与下游对齐排期，确认 11-10 联调窗口 |

## 三、按板块的量化句式

### 需求开发
- 完成 X 个需求（其中 P0 级 X 个），均已提测/上线
- 实现 X 功能的主体逻辑，覆盖率 X%，剩余 Y 部分（原因）

### 问题修复
- 修复缺陷 X 个：线上 P1 级 X 个、测试反馈 X 个
- 定位 X 问题的根因为 Y，修复后回归通过

### 技术建设
- 将 X 流程从手动改为脚本化，单次耗时从 A 降至 B
- 输出 X 文档/规范 1 份，已被 N 个成员/项目采用

### 协作沟通
- 组织/参与评审 X 次，形成决议 X 条
- 支持 X 团队排查 Y 问题，当日闭环

### 学习调研
- 调研 X 方向，产出对比结论：选 A 弃 B，理由 …

## 四、禁区

- 不编造数字。没有数据时写 `[待确认: 具体数字]`，交给用户补。
- 不用"显著提升""大幅降低"却不给基线。
- 不把计划写成事实（"即将上线"不是事实，"已提交上线审批"才是）。
